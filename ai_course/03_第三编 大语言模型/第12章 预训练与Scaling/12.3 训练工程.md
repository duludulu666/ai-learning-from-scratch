## 1. Engineering is part of the mathematical experiment

A paper may specify an optimizer and objective, yet an implementation can silently optimize something else: unequal token weighting, double scheduler steps, stale gradients or a restarted data order.

Start by defining a **logical batch**: all examples whose gradients contribute to one optimizer update. A microbatch is only a memory-management subdivision of that logical batch.

Let microbatch $i$ have summed target loss $S_i$ and valid target count $M_i$. The desired token-mean objective is

$$
L=\frac{\sum_i S_i}{M},\qquad M=\sum_i M_i.
$$

Because differentiation is linear,

$$
\nabla_\theta L=\sum_i\frac{\nabla_\theta S_i}{M}.
$$

Therefore call backward on each $S_i/M$, accumulate gradients, then step once. Dividing each microbatch mean by the number of microbatches works only when valid counts are equal.

## 2. Walk through an unequal example

Two microbatches have 2 and 6 valid targets. If their mean losses are 1 and 3, the correct weights are $2/8$ and $6/8$, giving 2.5. An equal average gives 2.

The same weights apply to gradients. The lab verifies full-batch gradients against microbatches of sizes 2 and 3 and includes an intentionally wrong mean-of-means negative control. An additional masked sequence test uses 2 and 5 valid targets and compares both gradients and the resulting AdamW update, so the check is not limited to unpadded classification.

Clip gradients after accumulation, not each microbatch separately, if you want the clipped full logical-batch gradient. Zero gradients before the logical batch and step the optimizer/scheduler at the intended update boundary.

Equivalence assumes independent per-example computation at the same parameter values. BatchNorm, different dropout samples and floating-point summation can invalidate exact equality; the lab's accumulation check uses a deterministic linear layer.

## 3. Mixed precision solves a resource problem

FP32 stores more precision than many neural-network operations require. FP16/BF16 can improve throughput and reduce some tensor storage on suitable hardware.

FP16 has a narrower exponent range than BF16 and is more vulnerable to underflow/overflow. Autocast chooses operation dtypes; it does not simply convert every tensor and reduction to the same low precision.

Loss scaling multiplies a loss by $s$ before backward, producing $s\nabla L$. Before an optimizer update, divide gradients by $s$. This protects small FP16 gradient values during computation without intentionally changing the update.

A CUDA-oriented sequence is shown as **pseudocode**, not a tested CPU lab:

```text
zero gradients
for each microbatch:
    autocast forward
    compute summed loss / total valid targets
    scaler.scale(loss).backward()
scaler.unscale_(optimizer)
clip accumulated gradients
scaler.step(optimizer)
scaler.update()
advance scheduler only according to the chosen successful-update convention
```

With true scalar gradient $g=0.01$, scale $s=1000$ and clip threshold 1, the scaled gradient is 10. Clipping that to 1 **before** unscaling produces 0.001, ten times too small. Unscale first to 0.01 and clipping correctly leaves it unchanged. A CPU arithmetic check demonstrates the order; it is not a CUDA AMP test.

Clipping scaled gradients before unscale uses the wrong effective threshold. Overflow may cause a skipped update; track actual optimizer updates separately from microbatch counts. BF16 often does not need loss scaling, but still requires finite-value checks. The local runtime is CPU-only: no GPU speedup or CUDA AMP correctness claim is made here.

## 4. Checkpointing has two different meanings

A model-selection snapshot needs the selected parameters and configuration. Exact continuation also needs optimizer moments, scheduler state, scaler state if used, update counters, data/sampler position, RNG states and data/tokenizer versions.

Dropout consumes random numbers. Restoring weights and optimizer but not the RNG can produce a different next update. A shuffled sampler may use its own generator, independent of the global PyTorch RNG.

The CPU lab saves model, AdamW, PyTorch RNG, dedicated sampler RNG, update index and configuration. In addition to next-step parameters/loss, it checks the restored AdamW step counters and first/second moments and verifies that omitting the moments changes the next update. It then runs one update, restores the saved state and verifies the **same next update exactly**, including dropout and batch order.

This fixture does not prove cross-GPU or cross-version bitwise reproducibility. Real data-loader workers, distributed ranks, Python/NumPy randomness and asynchronous pipelines require additional state or a documented replay policy.

Use trusted checkpoint files. Restricted loading such as `weights_only=True` reduces unsafe deserialization exposure, but untrusted artifacts still deserve isolation and provenance checks.

## 5. Distributed gradients need explicit normalization

In common data-parallel training each rank computes local gradients, then an all-reduce averages them. If rank $r$ has summed loss $S_r$ and the global valid count is $M$, the desired gradient is $\sum_r\nabla S_r/M$.

If the framework averages over $R$ ranks, backpropagating $R S_r/M$ on rank $r$ makes the resulting average match the global token mean. Averaging local means instead weights ranks equally even when their valid counts differ.

This is a derivation, not a distributed implementation in our CPU lab. Read the actual framework's reduction and gradient-accumulation conventions before applying a formula.

For two ranks with 2 and 6 valid tokens, write local mean-loss gradients as $\mathbf g_1,\mathbf g_2$. The desired gradient is $(2\mathbf g_1+6\mathbf g_2)/8$. Average-reducing local means gives $(\mathbf g_1+\mathbf g_2)/2$, which is different. Scaling each local sum by $R/M=2/8$ before average reduction yields the desired result. The extended CPU test simulates this reduction algebra without launching distributed workers.

Data parallelism replicates model parameters; tensor parallelism partitions operations; pipeline parallelism partitions layers. Sharded optimizer/state methods reduce replication. Communication, activation memory and load imbalance add costs beyond the simple parameter count.

## 6. Monitor interpretable quantities

Record loss sums/counts, learning rate, gradient norm before/after clipping, valid tokens per update, tokens/second, peak memory, overflow/skipped steps and validation metrics.

A loss spike can result from data composition, a scheduler jump, numerical failure or a malformed batch. Save enough metadata to reproduce the event without logging private raw text unnecessarily.

Compare curves against tokens and wall-clock time as well as update count. A larger batch changes what one update means. GPU timings require synchronization or device events; CPU timing does not establish GPU throughput.

## 7. Minimal gradient-accumulation check

```python
import copy
import torch
torch.manual_seed(2)
full = torch.nn.Linear(2,1).double()
split = copy.deepcopy(full)
x = torch.randn(5,2,dtype=torch.float64)
y = torch.randn(5,1,dtype=torch.float64)
((full(x)-y)**2).mean().backward()
for sl in [slice(0,2),slice(2,5)]:
    (((split(x[sl])-y[sl])**2).sum()/5).backward()
for a,b in zip(full.parameters(),split.parameters()):
    torch.testing.assert_close(a.grad,b.grad)
print("logical-batch gradient equivalence passed")
```
