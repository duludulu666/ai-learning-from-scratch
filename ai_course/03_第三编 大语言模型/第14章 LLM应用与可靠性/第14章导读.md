# 第 14 章：LLM 应用与可靠性

> 章节目标：把模型调用放入一个可观察、可验证、可恢复的应用系统，而不是把一次漂亮的聊天输出当作产品质量。

第三编目录 · 前置：第 13 章

## 本章结构

| 小节 | 要回答的问题 | 主要产出 |
|---|---|---|
| 14.1 Prompt结构化输出与工具调用 | 如何约束输出并安全地调用外部功能？ | 定义输出契约，区分拒答/不完整状态，测试本地校验与工具分派 |
| 14.2 RAG与外部知识 | 如何让回答有外部依据？ | 实现词法检索与引用 fixture，解释 embedding/reranking 和真实 grounding 评测 |
| 14.3 Agent基础 | Agent 到底是什么？ | 实现有边界、审批、日志、幂等重试与故障测试的本地控制器 |

## 关键原则

应用系统至少要能回答：

1. 模型看到了什么上下文？
2. 它输出了什么结构？
3. 哪一个工具被调用，参数是否通过验证？
4. 工具失败后如何重试、回退或请求人工确认？
5. 如何用 task-specific evals 证明改动真的有帮助？

对于 OpenAI API 应用，官方文档强调：Structured Outputs 用 JSON Schema 约束响应结构，并让拒答等边界状态可程序化处理；function/tool calling 是“模型提出调用 → 应用执行并返回 tool output → 模型继续”的多步循环。不要把模型生成的工具参数直接当作可信命令。

## 章节出口标准

你能在本地无 API 的模拟环境中构建一个 schema 校验器、检索器和受限工具循环；能列出 prompt injection、越权调用、无依据回答和评测泄漏的测试用例；能为每个失败案例定义可观测日志字段。

官方参考：[Structured Outputs](https://developers.openai.com/api/docs/guides/structured-outputs)、[Function Calling](https://developers.openai.com/api/docs/guides/function-calling)、[Evaluation best practices](https://developers.openai.com/api/docs/guides/evaluation-best-practices)、[Agent safety](https://developers.openai.com/api/docs/guides/agent-builder-safety)。
