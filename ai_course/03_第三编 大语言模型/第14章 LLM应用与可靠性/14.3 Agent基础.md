> Prerequisites: 14.1 tool contracts and 14.2 retrieval trust boundaries. Goal: reason about agents as stateful controllers with bounded authority, not as unbounded loops.

## 1. What makes a system agentic?

A fixed workflow follows a predefined sequence. An agentic system lets a policy choose some next actions based on the current task and observations. That policy may be an LLM, but the surrounding program still manages state, tools and permissions.

Planning text alone does not execute a plan. Memory is not automatically reliable. A model saying “done” does not establish that the requested external state was reached.

We separate the policy that proposes actions from the controller that checks and executes them.

## 2. Define the state transition

Let $s_t$ contain the user goal, allowed capabilities, verified observations, pending actions and remaining budget. The policy proposes $a_t$; a validator determines whether it is allowed. A tool then returns observation $o_{t+1}$ and the controller updates state:

$$
a_t\sim\pi(\,\cdot\mid s_t),
\qquad
o_{t+1}=\mathrm{tool}(a_t),
\qquad
s_{t+1}=F(s_t,a_t,o_{t+1}).
$$

These symbols describe a system interface, not a training algorithm. A denied action produces a denial state rather than executing and hoping to undo it later.

The executor now checks that `result.call_id` matches the pending proposal before accepting the observation. A mismatched result yields `needs_attention` rather than being attached to the wrong action. This validates correlation, not arbitrary result content or the truth of a remote service.

Trusted permissions must come from application/user authorization, not from retrieved documents or model-generated claims.

## 3. Make terminal conditions explicit

A controller needs distinct endings:

- operations completed: the proposed queue finished, but goal achievement has not been verified;
- completed: operations finished and an explicit task-specific goal check passed;
- goal not verified: the queue finished but the supplied goal predicate returned false;
- rejected: proposal or execution arguments were invalid;
- needs approval/access: a permission boundary prevented execution;
- needs attention: repeated tool failure requires intervention;
- budget exceeded: the allowed call or time budget was exhausted.

Do not label a budget timeout as success. Do not retry an unauthorized operation until it “works.” Validation, authorization, transient failure and business failure need different handling.

The local controller caps proposed calls and attempts per call. With at most 3 proposals and 2 attempts each, up to 6 execution attempts can occur; `max_calls` does not mean a global three-attempt budget. A real system also needs elapsed-time, token, spending and output-size limits, cancellation and tool-specific timeouts.

## 4. Retry is safe only when consequences are understood

A tool can commit an action but lose the response. Retrying blindly can duplicate a payment, email or reservation.

An idempotency key identifies one intended operation. The authoritative service stores its argument signature and result. Repeating the same key and arguments returns the original result instead of repeating the side effect.

Reusing the same key with different arguments must be rejected. Scope keys by user/tenant and operation, and enforce retention and transactional consistency. Merely caching a result in the model's conversation is not sufficient.

Our in-memory reservation fixture simulates “commit succeeded, response timed out.” A retry with the same key returns the cached result; the reservation counter increases only once.

This proves the controller's behavior against the fixture. Production exactly-once effects require guarantees from the external service or a carefully designed transactional protocol.

## 5. Approval must bind to the exact operation

The fixture approval record binds actor, call ID and canonicalized arguments. A changed count cannot reuse approval for the earlier operation.

The controller rejects a reservation without this trusted record even if a document says “Approval: true.” This illustrates a security boundary outside the model.

For high-impact operations, show the user the exact target and consequence. Approval should not be inferred from unrelated earlier actions or fabricated model text. Read-only tools may still expose private data, so data access also needs checks.

## 6. Recovery needs authoritative state

A resumable agent should persist task ID, versioned state, pending action IDs, tool results, approval references and budget counters. After a crash, reconcile uncertain pending actions with the authoritative tool before inventing a new action ID.

The lab replays the same call against the same in-memory store to test idempotency. Returned results and cache entries are now separate snapshots: mutating an output dictionary must not corrupt the authoritative result used by a retry. A second actor cannot reuse the first actor's approval, while the same call ID with a separate valid approval belongs to a different actor-scoped operation. It does not persist a durable distributed state machine or recover after an actual process crash. Those are engineering extensions.

Keep observations separate from beliefs. A plan to reserve a room is not evidence that a reservation exists; only a verified tool result can support that claim.

## 7. Memory and context are selective views

Conversation history, a state database and retrieved long-term memory serve different roles. Context summarization can omit crucial constraints or misstate an earlier result.

Store critical permissions, exact operation IDs and structured task state outside lossy natural-language summaries. Retrieve only authorized relevant memory, preserve provenance and provide deletion/retention policies for sensitive data.

When the context is long, a compact verified state snapshot can help, but the model's generated summary should not silently become a source of new authority.

## 8. Observe actions, not just final prose

A useful trace includes task/call IDs, tool name, attempt number, validation decision, start/end status, sanitized error class and result provenance. Avoid logging secrets or unnecessary full documents.

Evaluate at multiple levels:

- proposal validity and tool selection;
- argument correctness and permission enforcement;
- tool recovery and duplicate-effect rate;
- final task success, cost and latency;
- malicious-document and ambiguous-request behavior.

A long plan or confident final answer is not an objective success metric. Pairwise model judgments can supplement checks but should not replace executable task evidence.

## 9. The offline controller experiment

`lab_14_3.py` uses a **scripted queue of proposals**, not a live LLM planner. It verifies:

1. an unapproved reservation is denied;
2. an approved read/reservation sequence succeeds;
3. a timeout after commit triggers a safe retry;
4. replay does not duplicate the side effect;
5. changed arguments under the same key are rejected;
6. call budgets, retry limits and private-document access are enforced;
7. a malicious proposal induced by untrusted text still lacks authority.

The seventh case tests the boundary even after assuming the policy was fooled. It does not claim the model itself detects every injection.

Additional tests distinguish an empty/completed proposal queue from a satisfied goal, reject mismatched tool result IDs, separate approvals across actors and protect cached results from mutation. `run_calls` defaults to `operations_completed` when no goal checker is provided; only an explicit boolean `goal_check(outputs)` can produce `completed`.

A goal checker must itself reflect the user's actual request. Checking “one tool ran” is insufficient for a request requiring three verified outputs. The fixture's checker validates only a small known lookup result; it is not a universal success oracle. If a timeout occurs after the final allowed attempt, a side effect may already exist—`needs_attention` must prompt reconciliation, not a fresh operation ID that duplicates it.

```python
# A tiny state-transition invariant, independent of any language-model API.
state = {"pending": "op-1", "confirmed": set()}
tool_result = {"operation_id": "op-1", "status": "ok"}
if tool_result["status"] == "ok" and tool_result["operation_id"] == state["pending"]:
    state["confirmed"].add(tool_result["operation_id"])
    state["pending"] = None
assert state["pending"] is None and "op-1" in state["confirmed"]
print("completion follows a matched tool result")
```
