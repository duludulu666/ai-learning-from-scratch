## 1. “The model is slow” is not yet a diagnosis

A workload can wait on arithmetic, memory movement, kernel launch overhead, synchronization, data loading, or communication. Reducing parameter count helps some of these and not others.

This chapter develops a resource ledger first, then measures a small CPU operation. It does not claim access to a GPU benchmark. Hardware-independent arithmetic and actual hardware timings must remain separate.

Prerequisites: matrix multiplication, Transformer shapes, and the budget introduction in 10.3.

## 2. Count operations for one matrix multiplication

Let $\mathbf{X}\in\mathbb{R}^{B\times K}$ and $\mathbf{W}\in\mathbb{R}^{K\times N}$. Output $\mathbf{Y}=\mathbf{X}\mathbf{W}$ has $BN$ entries, each a sum of $K$ products.

Using the common convention of two floating-point operations per multiply-add gives approximately

$$
F=2BKN
$$

FLOPs. This ignores the difference of one addition per dot product and other operations such as bias or activation.

If every input and weight is read once and the output is written once, with $s$ bytes per scalar, ideal data movement is

$$
Q=s(BK+KN+BN).
$$

This is a simplified minimum traffic model for this standalone operation, not a measurement of cache or GPU memory transactions. Real tiling, reuse, layout conversions, and repeated reads change traffic.

Define arithmetic intensity $I=F/Q$, in FLOP/byte. It tells us how much arithmetic is available per byte moved under the stated model.

### Backward has its own operation count

For upstream output gradient $\mathbf{G}_Y\in\mathbb{R}^{B\times N}$, matrix differentiation gives

$$
\mathbf{G}_X=\mathbf{G}_Y\mathbf{W}^{\mathsf T},
\qquad
\mathbf{G}_W=\mathbf{X}^{\mathsf T}\mathbf{G}_Y.
$$

Each multiplication has approximately $2BKN$ FLOPs. If both gradients are required, forward plus backward is about $6BKN$, before bias, activation, optimizer work, or recomputation. Freezing $\mathbf{W}$ can remove its gradient computation, but an upstream trainable connector may still require $\mathbf{G}_X$.

Count at a specified memory boundary. “Read each tensor once” is a cold-input model for that boundary; repeatedly benchmarking tiny arrays may keep them in cache, so comparing those timings with DRAM bandwidth is not a valid roofline diagnosis.

## 3. Derive a roofline lower bound

Suppose a device can sustain at most $P_{\max}$ FLOP/s and bandwidth $\beta_{\max}$ byte/s for the relevant workload. Arithmetic alone requires at least $F/P_{\max}$ seconds, and data movement requires at least $Q/\beta_{\max}$ seconds.

Even with perfect overlap, time cannot be lower than the slower requirement:

$$
t\geq\max\left(\frac{F}{P_{\max}},
\frac{Q}{\beta_{\max}}\right).
$$

Equivalent attainable throughput is bounded by $\min(P_{\max},\beta_{\max}I)$. This is an optimistic ceiling, not a prediction; small kernels often fall well below it due to overhead or poor utilization.

中文确认：roofline 是“理想情况下也不能超过的上限”，不是把峰值参数代入就能得到真实运行时间。

For $B=8,K=128,N=64,s=4$, $F=131{,}072$ and $Q=38{,}912$ bytes, so $I\approx3.368$ FLOP/byte. The companion uses hypothetical peak and bandwidth values only to illustrate the bound, clearly labeled as hypothetical.

## 4. Why batching can change the bottleneck

At $B=1$, the weight matrix may dominate movement while providing relatively little reuse per load. Increasing $B$ lets the same weights serve more examples in a matrix-matrix operation, increasing arithmetic intensity.

But batching also increases activations, queueing delay, and cache memory. A larger batch can improve total tokens/second while worsening an individual request's waiting time. Throughput and latency are not interchangeable.

Autoregressive decoding often generates one new token per sequence per step, while prompt prefill processes many prompt tokens together. Their matrix shapes and memory reuse differ. “The model is compute-bound” is incomplete without specifying prefill/decode phase, batch, context length, dtype, and hardware.

## 5. Memory is a ledger, not just the parameter file

For $P$ parameters in pure FP32 Adam training, a simplified persistent ledger is:

| Item | Bytes per parameter |
|---|---:|
| Parameters | 4 |
| Gradients | 4 |
| First moment | 4 |
| Second moment | 4 |
| Total before activations and workspaces | 16 |

Thus 1,000 parameters use about 16,000 bytes for these four arrays. Real implementations may allocate state lazily and add temporary buffers. Mixed-precision training can add master weights or use different state dtypes; there is no universal 16-byte rule for every optimizer implementation.

Training also stores activations needed for backward. Attention scores, FFN hidden states, and sequence length can dominate. Activation checkpointing saves fewer intermediates and recomputes them during backward, trading compute for memory.

Inference removes optimizer states and gradients but introduces KV cache for autoregressive serving. Quantizing weights does not automatically quantize activations or cache.

## 6. Timing requires a workload contract

For CPU timing, warm up, set thread count, repeat, and report a robust summary. For GPU timing, asynchronous launches require device synchronization or correctly placed device events; wall-clock timing around an unsynchronized launch measures submission rather than completion.

Record shape, dtype, device, thread count, batch, sequence lengths, warmup, repeats, measured region, and whether data transfer/preprocessing is included. End-to-end latency is different from a kernel-only timing.

```python
import time
import statistics
import torch
torch.set_num_threads(1)
x, w = torch.randn(8, 128), torch.randn(128, 64)
for _ in range(10):
    x @ w
times = []
for _ in range(7):
    start = time.perf_counter()
    for _ in range(500):
        x @ w
    times.append((time.perf_counter() - start) / 500)
print("CPU median microseconds:", statistics.median(times) * 1e6)
```

This includes Python-loop and dispatch overhead and does not isolate a GPU kernel. Tiny timing values vary across runs and machines; do not use them as universal model-speed claims.

## 7. Profiling before optimization

A profiler can attribute time and memory to operations, but profiler overhead can distort short workloads. Start with a stable representative workload, identify a bottleneck, change one factor, and rerun a non-profiled benchmark plus correctness tests.

Distinguish allocated tensor memory from memory reserved by a caching allocator, and peak from end-of-run memory. Releasing a tensor does not necessarily return reserved memory to the operating system immediately.

A faster implementation must preserve the intended outputs or document an acceptable error/quality tradeoff. Speed without the same workload and quality target is not a controlled comparison.

### Verify recomputation separately from performance

The companion now compares normal execution with PyTorch activation checkpointing on the same small MLP and inputs. Output-loss gradients for inputs and every parameter must match. This is a CPU correctness test, not a measurement of peak GPU memory saved.

For stochastic blocks, recomputation must reproduce the relevant random choices; stateful updates also need care. Dropping saved activations without faithfully reconstructing the original computation changes the backward problem.

For serving, report time to first token (including the stated queue/prefill boundary), inter-token latency, end-to-end request latency, and total generated tokens divided by elapsed time separately. A throughput increase can coexist with worse time to first token. Seven loop averages in the toy benchmark are not enough to estimate production p99 latency.

Self-check: with $K=128,N=64,s=4$, batch sizes 1, 8, and 64 give arithmetic intensities approximately .489, 3.368, and 12.8 FLOP/byte under the same ideal traffic model. The companion's timed shape remains $B=8$; these other values are arithmetic estimates, not measured speedups.
