## 1. Several devices introduce two separate questions

How is work partitioned, and how are updates made equivalent to the intended objective? A program can run on several devices yet optimize the wrong weighted loss.

Data parallelism replicates parameters and splits examples. Tensor parallelism partitions operations/tensors within a layer. Pipeline parallelism places successive layers on different devices. Optimizer/state sharding distributes persistent storage. These can be combined, but each adds communication and state-management constraints.

Our laboratory simulates the algebra in one CPU process. It launches no process group and measures no network or multi-GPU performance.

## 2. Data parallelism with equal local sizes

Let $R$ ranks each have $n$ examples and identical parameters $\theta$. Rank $r$ computes its local mean loss $L_r$ and gradient $\mathbf{g}_r=\nabla_\theta L_r$.

For the global example mean,

$$
L=\frac{1}{R}\sum_{r=1}^{R}L_r,
\qquad
\nabla_\theta L=\frac{1}{R}\sum_{r=1}^{R}\mathbf{g}_r.
$$

An all-reduce combines gradients; whether a particular primitive returns a sum or average must be checked. Standard DDP semantics are commonly discussed as averaging gradients across ranks. All ranks then apply the same optimizer update to stay synchronized.

This equivalence assumes per-example losses decompose appropriately. Training-mode BatchNorm, different random dropout realizations, or other batch-coupled operations can change equivalence to a single larger batch.

## 3. Unequal valid-token counts change the weights

Suppose rank $r$ has $n_r$ valid response tokens and local summed loss $S_r$. The desired global token mean is

$$
L=\frac{\sum_{r=1}^{R}S_r}{N},
\qquad
N=\sum_{r=1}^{R}n_r.
$$

If each rank backpropagates $S_r/n_r$ and DDP averages, it weights ranks equally, not tokens. With 2 tokens on one rank and 3 on another, the two-token rank gets too much weight.

To compensate for a reducer that divides by $R$, rank $r$ can backpropagate

$$
\widetilde L_r=\frac{R S_r}{N}
=\frac{Rn_r}{N}\left(\frac{S_r}{n_r}\right)
$$

when $n_r>0$. Averaging its gradient across ranks then produces $\nabla(\sum_rS_r/N)$.

If $n_r=0$, avoid forming a local mean; use a graph-connected zero sum as appropriate and ensure every rank participates in required collectives. If global $N=0$, coordinate skipping the update. Accumulation across several microbatches requires the total valid count for the intended effective batch, not a separate arbitrary mean for each microbatch.

## 4. A scalar hand example

Rank 1 has two token gradients $(1,1)$; rank 2 has three token gradients $(3,3,3)$. The global mean is

$$
g=\frac{1+1+3+3+3}{5}=2.2.
$$

Naive mean-of-means gives $(1+3)/2=2$. Correct local scaling gives $(2\cdot2/5)(1)=.8$ and $(2\cdot3/5)(3)=3.6$; the reducer average is $(.8+3.6)/2=2.2$.

The companion checks the same principle on an actual linear classifier with autograd and verifies every parameter gradient against the full batch.

## 5. Tensor partitions: concatenate or sum?

For row-vector inputs $\mathbf{X}$ and mathematical weight $\mathbf{W}\in\mathbb{R}^{d_{\mathrm{in}}\times d_{\mathrm{out}}}$, output is $\mathbf{Y}=\mathbf{X}\mathbf{W}$.

Partition output columns, $\mathbf{W}=[\mathbf{W}_1\ \mathbf{W}_2]$. Then

$$
\mathbf{Y}=[\mathbf{X}\mathbf{W}_1\ \mathbf{X}\mathbf{W}_2].
$$

Outputs concatenate; no sum is needed to obtain separate output coordinates.

Partition the input dimension, $\mathbf{X}=[\mathbf{X}_1\ \mathbf{X}_2]$ and $\mathbf{W}=[\mathbf{W}_1^{\mathsf T}\ \mathbf{W}_2^{\mathsf T}]^{\mathsf T}$. Then

$$
\mathbf{Y}=\mathbf{X}_1\mathbf{W}_1+\mathbf{X}_2\mathbf{W}_2.
$$

Partial outputs sum. A bias must be added once after summation, not once per partition. PyTorch stores the transpose of this mathematical weight; the lab explicitly partitions the corresponding axes.

### A zero-token rank and an empty global batch are different

With a nonempty global batch, a rank with no valid tokens still contributes a graph-connected zero and participates in the same collective sequence. Selecting an empty tensor slice and summing it avoids reading ignored values; multiplying a potentially NaN loss by zero does not.

The extended CPU test adds a third rank with zero tokens and verifies that the three-rank average still matches the full-batch gradient. This verifies the normalization algebra, not actual DDP collective scheduling.

If **every** rank has zero valid tokens, skip the optimizer update consistently across ranks. Giving the optimizer zero-valued gradients and calling `step()` is not always a no-op: AdamW weight decay or old momentum can still move parameters. The lab demonstrates this with nonzero decay. Scheduler/scaler progression must follow the explicitly chosen skipped-step policy.

For $P$ FP32 parameters, an illustrative persistent-state ledger is $16P$ bytes per rank without sharding; sharding only Adam moments gives $8P+8P/R$; additionally sharding gradients gives $4P+12P/R$; ideal sharding of all four arrays gives $16P/R$. These are storage-accounting models, excluding temporary gathered parameters, activations, buffers, uneven partitions, and communication. They explain the potential saving without promising actual peak memory.

Different dropout samples prevent exact replay equality but do not themselves create an incorrectly weighted objective. BatchNorm is different because it couples examples through local batch statistics. Separate random-realization differences from a mathematical loss-normalization error.

## 6. Communication and pipeline utilization

A rough ring all-reduce traffic model for gradient size $G$ bytes and $R>1$ ranks transfers approximately $2(R-1)G/R$ bytes per rank across reduce-scatter and all-gather. Latency, topology, contention, and overlap affect time; byte count alone is not a throughput benchmark.

For an idealized forward-only pipeline with $p$ equal-time stages and $m$ microbatches, a fill/drain schedule takes $m+p-1$ stage-time slots. Ideal utilization is

$$
U=\frac{m}{m+p-1}.
$$

For $p=4,m=8$, $U=8/11$. This simple formula is not a universal training-pipeline efficiency law: backward scheduling, activation storage, stage imbalance, and communication change it.

More microbatches can reduce bubbles but increase overhead and complicate optimization bookkeeping. Sharding optimizer states saves memory but adds communication and checkpoint coordination.

## 7. Recovery is part of correctness

A useful checkpoint includes model parameters, optimizer state, scheduler/scaler state when used, RNG state, sampler position, global step, and configuration/data versions. Distributed checkpoints additionally need a consistent view across ranks and a compatible restoration/sharding plan.

The lab restores actual AdamW parameters and moment state in a deterministic CPU example and verifies the next step matches. It omits stochastic layers and distributed failures, so it does not claim full distributed fault tolerance.

A real system should test interrupted writes, rank failure, incomplete checkpoints, and changed world size. Do not call a collection of weight files “exactly resumable training” unless the necessary state and replay conditions are established.

### Standalone mean-of-means counterexample

```python
import torch
local_means = torch.tensor([1., 3.], dtype=torch.float64)
counts = torch.tensor([2., 3.], dtype=torch.float64)
naive = local_means.mean()
scaled_local = 2 * counts / counts.sum() * local_means
correct = scaled_local.mean()
torch.testing.assert_close(correct, torch.tensor(2.2, dtype=torch.float64))
assert naive.item() == 2.0
```

The number 2 in `scaled_local` is the rank count, not an extra loss weight. It cancels the simulated reducer's division by 2.
