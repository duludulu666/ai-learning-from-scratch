## 1. Capability, alignment, and deployment safety are different questions

Capability asks whether a system can perform a task. Alignment asks whether its learned behavior follows intended objectives and constraints across relevant situations. Deployment safety asks whether the complete system manages risks within its actual authority and environment.

A model can be capable but optimize the wrong proxy. A well-intentioned response can still be factually wrong. A carefully prompted model can still propose an unauthorized action. Training, evaluation, and application controls must complement each other.

This section is a foundation for further study, not a claim that alignment is solved or that the toy tests certify a real model.

## 2. A proxy objective can diverge from the real goal

Suppose a summarizer is rewarded for response length because longer answers initially correlate with detail. The real goal is supported, useful information. Once optimized, the system can add unsupported details to increase length.

Let proxy reward be $r_{\mathrm{proxy}}$ and true utility be $u$. Maximizing $\mathbb E[r_{\mathrm{proxy}}]$ does not imply maximizing $\mathbb E[u]$ unless the proxy preserves the relevant ordering under the optimized distribution.

A concrete fixture: a concise answer has one claim, supported by evidence. A longer answer keeps that claim and adds four unsupported claims. Length increases while support precision falls from $1/1$ to $1/5$.

This is a constructed proxy-failure example, not a trained reward model. In real experiments, define observable failure criteria and test whether optimization changes the proxy/utility relationship.

## 3. Preference training and verifiable rewards have boundaries

SFT teaches demonstrated responses. Preference optimization, including DPO from 13.3, teaches relative choices under a dataset and reference setup. Reinforcement learning can optimize rewards for sampled behavior. None guarantees correctness outside the reward's coverage.

Verifiable tasks, such as executing a bounded unit test, can provide stronger feedback than vague preferences. But incomplete tests can still reward brittle shortcuts; a program that passes known tests may fail unseen cases.

A useful research question is not “Does alignment work?” but “Under a specified training signal, what behavior improves, what regresses, and how robust is the improvement under a held-out distribution?”

## 4. Authority should not come from model confidence

Consider a model-generated proposal containing an action, resource ID, and confidence. Confidence is a prediction, not permission.

A deterministic application gate should validate the schema, action allowlist, resource scope, and required approval. A high-confidence request to access a private resource remains unauthorized. Text claiming “system authority” inside an image, retrieved page, or tool result remains untrusted content.

The companion tests 12 hand-authored proposals plus scope and approval invariants against a local policy gate. It executes no real tool action. The gate's resource IDs are synthetic strings, not filesystem paths, and it is not presented as a complete sandbox.

Defense in depth includes least privilege, scoped credentials, evidence and instruction separation, explicit approval for consequential actions, bounded execution, privacy-aware logging, and failure recovery. A prompt or schema alone does not eliminate injection or data leakage.

### Bind approval to the exact proposed operation

Approving “write to note A” is ambiguous if the model can change the payload afterward. The revised fixture separates a permitted-resource scope from explicit approvals, and an approval binds $(\text{action},\text{resource},\text{payload})$.

A write to an out-of-scope resource is denied even if an approval-shaped tuple exists. An in-scope write with changed text needs new approval. A previously approved exact payload can pass regardless of whether model confidence is .1 or 1.

The approval set is a **trusted fixture input**, not a field supplied by the model. Real systems additionally need authenticated user decisions, resource/version binding, expiry/revocation, protection against time-of-check/time-of-use changes, idempotency, and audit trails. The code does not implement those production mechanisms.

Do not collapse “denied” and “needs approval”: some actions are outside the application's permitted scope and should not be offered as ordinary confirmation requests. The tests preserve this distinction without accessing any real resource.

## 5. Zero observed failures does not mean zero risk

Suppose $n$ independent representative trials each have unknown failure probability $p$. If no failures are observed, the probability of that outcome is

$$
P(0\text{ failures}\mid p)=(1-p)^n.
$$

For a one-sided 95% upper confidence limit, set this probability to .05 and solve:

$$
(1-p_{\mathrm{upper}})^n=.05,
\qquad
p_{\mathrm{upper}}=1-.05^{1/n}.
$$

For $n=100$, the upper limit is approximately .0295. Using $\log(1-p)\approx-p$ for small $p$ gives the “rule of three,” approximately $3/n$.

This calculation assumes independent Bernoulli trials representative of the intended use. Correlated fixtures, cherry-picked tests, distribution shift, and adaptive attackers invalidate a naive interpretation. Passing handcrafted gate tests cannot justify using their fixture count as $n$ in this formula to estimate deployment risk.

```python
n = 100
upper = 1 - .05 ** (1 / n)
assert .029 < upper < .030
print("Illustrative one-sided 95% upper bound:", upper)
```

The mathematical check and policy-gate fixtures are separate experiments with separate claims.

## 6. Bias and subgroup evaluation

Aggregate quality can hide unequal error across language, region, device quality, accessibility needs, or other relevant groups. Identify groups ethically and lawfully, preserve privacy, and report group support and uncertainty.

Different fairness criteria can conflict, especially when base rates differ. Do not present one parity metric as a universal fairness definition. Choose criteria with affected stakeholders and the task's error costs in mind.

Small groups can have wide uncertainty. Suppressing a group's result because it is inconvenient is not analysis; reporting it as precise without enough data is also misleading.

## 7. Interpretability: prediction about mechanisms needs interventions

An attention heatmap or feature correlation suggests a hypothesis but does not by itself explain causation. A stronger workflow identifies a proposed mechanism, makes an intervention, predicts its effect, and tests on held-out cases.

Interventions can introduce distribution shift. Removing a feature may disrupt many computations simultaneously. Describe the intervention's scope and alternative explanations.

Useful directions include representation probing, activation interventions, sparse feature decompositions, and circuit hypotheses. These are research families, not proven windows into every decision of a frontier model.

### From a probe to a mechanism hypothesis

A probe predicting a label from hidden states shows that the representation contains usable information for that probe. It does not show that the original model used that information to make its answer.

For example, hidden state $(h_1,h_2)$ may encode both shape and background, while the output head reads only $h_2$. A probe can accurately recover shape from $h_1$ even though the actual output ignores it. To test use, intervene on $h_1$ while preserving a justified control distribution and predict an output change; a null change or an off-distribution intervention needs careful interpretation.

For subgroup reporting, a system with 90 correct among 100 cases in group A and 1 correct among 10 cases in group B has aggregate accuracy $91/110\approx82.7\%$ but group accuracies 90% and 10%. Report supports and intervals before attributing the difference to a mechanism. This arithmetic fixture is not evidence about any real demographic group.

## 8. A research map based on prerequisites, not hype

| Direction | Prerequisites from this book | A bounded next experiment |
|---|---|---|
| Multimodal grounding | ViT, contrastive loss, cross-attention, response masks | Compare image interventions and unanswerable questions under a fixed rubric |
| Post-training and reasoning | SFT, preference objectives, decoding, eval design | Compare verifier-guided candidate selection with a fixed inference budget |
| Efficient inference | Cache math, precision, profiling | Measure one optimization at fixed quality on hardware you actually have |
| Generative modeling | VAE likelihoods, diffusion, score intuition | Compare a new sampling rule with a matched noise schedule and sample diagnostics |
| Reliability and safety | Splits, uncertainty, authority gates | Build a held-out failure suite and analyze one regression class |
| Interpretability | Gradients, representations, interventions | Test one mechanism hypothesis with matched controls |

These are durable directions, not claims about the latest unpublished architectures or hiring requirements. Entry into a research lab depends on demonstrated ability, role fit, collaboration, and opportunities; no curriculum guarantees employment.

For a new paper, separate what it proves, what it measures, and what it speculates. Reproduce a narrow result before attempting a full-scale system. Record paper version, code revision, data, compute, baseline, assumptions, and failed replications.

## 9. A practical paper-to-experiment workflow

Choose one question you can test with available compute. Read the abstract for the claim, the method for the mechanism, and the experimental section for the actual comparison. Re-derive one central equation and identify what would falsify the proposed benefit.

Implement a minimum baseline before the new method. Match evaluation and tuning budgets, run multiple seeds where affordable, keep the holdout independent, and report limitations in English. Negative results are useful when the protocol is credible and the explanation is specific.

For your learning, produce one concise technical note per topic: claim, derivation, implementation, test, failure, and next question. This gives future conversations a durable evidence trail without pretending that generated courseware is already mastered.
