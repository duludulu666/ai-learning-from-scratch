## 1. Make improvement observable before making the system complex

An eval is a repeatable test of an AI system against a defined objective. It can evaluate a model, a prompt, a retrieval stage, a tool controller, or an entire workflow. A unit test of the evaluator is different from an evaluation of the model.

The loop is: specify the task, collect representative cases, define scoring, establish a baseline, change one hypothesis, compare, inspect errors, and decide whether to promote. The result may be “do not ship”; that is a successful evaluation outcome.

Official OpenAI evaluation guidance emphasizes task-specific tests, early evaluation, representative and edge cases, and calibration of automated graders against human judgment. These are portable engineering principles. This chapter implements a local harness, not a hosted API workflow.

## 2. A test case is more than a prompt

Each case needs a stable ID, input, expected behavior or rubric, relevant slice, and provenance. Some tasks have exact answers; others need a rubric or executable outcome check.

Examples of distinct scoring levels:

| Level | Example question | Typical checker |
|---|---|---|
| Format | Is the output schema valid? | Parser and schema validation |
| Task | Does the answer address the question correctly? | Exact answer, executable test, or calibrated rubric |
| Evidence | Are claims supported by the supplied source? | Claim/evidence annotation |
| Control | Was an unauthorized action prevented? | State and permission tests |
| Operations | Is latency/cost within the stated budget? | Real measurement under a defined workload |

Passing the first level does not imply passing the others. A perfectly valid JSON object can contain an incorrect answer.

## 3. Define the promotion rule before the comparison

Let $M_b,M_c$ be baseline and candidate quality metrics, $S_b,S_c$ a critical-slice metric, and $C_c$ candidate cost or latency. One illustrative rule is

$$
\mathrm{promote}
=(M_c\geq M_b)
\land(S_c\geq S_b-\delta)
\land(C_c\leq C_{\max}).
$$

Here $\delta\geq0$ is a predeclared tolerated critical-slice regression and $C_{\max}$ is a resource cap. The logical AND means all conditions must hold. A real decision should also consider sample size, uncertainty, severity, and independent review; this formula is only a transparent starting point.

For four cases, suppose the baseline gets one common case plus the critical case correct: accuracy .5 and critical accuracy 1. A candidate gets all three common cases correct but fails the critical one: accuracy .75 and critical accuracy 0. With $\delta=0$, it must not be promoted despite a better average.

## 4. Separate development feedback from final evidence

A regression suite grows from known failures and should run frequently. Developers see it and intentionally improve it. It therefore becomes development evidence.

A locked holdout estimates performance on cases not used to select the change. Inspect it only at planned decision points. If you repeatedly tune against it, relabel it as development data and obtain a new justified holdout.

For stochastic generation, specify decoding settings and repeated samples. Distinguish per-sample success, pass-at-least-once under a candidate budget, and the success of the actual deployed selection rule. Generating ten candidates and checking whether any is correct is not the same as producing one reliable answer.

## 5. Automated graders also need evaluation

Exact match is cheap and reproducible but may reject valid paraphrases. Executable checks are powerful when a task has verifiable outputs, but incomplete tests can be gamed. Model judges scale human-like rubrics but can have position, verbosity, self-preference, and domain biases.

To calibrate a judge:

1. Write anchored examples of pass, partial success, and fail.
2. Collect independent human labels on a representative subset.
3. Blind system identity and randomize answer order for pairwise judging.
4. Measure agreement and inspect disagreements by slice.
5. Version the rubric, judge model/settings, and scoring code.
6. Recheck after distribution or judge changes.

Treat candidate responses as untrusted data for a grader; instructions inside them must not override the rubric. A judge should not receive permission to execute arbitrary candidate text.

## 6. Runnable decision counterexample

```python
baseline = {"accuracy": .50, "critical": 1.0, "latency_ms": 10}
candidate = {"accuracy": .75, "critical": 0.0, "latency_ms": 12}
promote = (
    candidate["accuracy"] >= baseline["accuracy"]
    and candidate["critical"] >= baseline["critical"]
    and candidate["latency_ms"] <= 15
)
assert not promote
```

These latency numbers are **hand-authored fixtures**, not measured inference times. The full companion validates case IDs, output completeness, finite nonnegative latency fields, slice scores, and the rejection rule. It calls no model or API.

Replacing fixtures with a model requires an adapter that records actual requests, outputs, errors, seeds/settings where supported, and measured timings. Keep secrets and personal data out of logs; retain only authorized data with a clear retention policy.

### Stochastic outcomes: what is the independent unit?

If one prompt has success probability $p$ and independent attempts share that probability, at least one success among $k$ attempts has probability

$$
P(\text{at least one success})=1-(1-p)^k.
$$

For $p=.5,k=4$, this is .9375, not .5. But a deployed system only benefits if its selection rule can identify a successful candidate. The calculation is not a model-evaluation result, and correlated attempts violate its independence assumption.

When each case has several sampled outputs, retain case IDs and sample indices. For case-level generalization, resample cases together with their within-case outputs; counting each sampled output as a new independent task understates uncertainty. Also report failures/timeouts rather than silently dropping them.

The local harness now rejects boolean/string latencies, malformed output tuples, invalid case IDs, and extra outputs. Python's `bool` is a subclass of `int`, so “numeric” validation must explicitly reject it when it has no legitimate timing meaning.

## 7. A practical experiment record

Use a compact report with: hypothesis; dataset and split versions; baseline and candidate identifiers; changed factor; scoring and grader versions; aggregate and slice results; uncertainty; cost/latency measurement conditions; gained and regressed examples; decision and next hypothesis.

Do not rewrite a failing case to make the change pass. Correct genuine annotation errors with an auditable reason and rerun all compared systems.

Operational monitoring complements pre-release evals. It should detect distribution drift, new failure categories, and unexpected costs. Do not automatically feed private production logs into training; consent, access control, and data minimization still apply.
